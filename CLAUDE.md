# CLAUDE.md — Сайт-портфоліо фотографа

## 1. Контекст проєкту

**Замовник:** фотостудія / фотограф. Зараз усе лежить в Instagram, але там «все не влазить».
**Що потрібно:** сайт-галерея з фото за категоріями (весілля, хрестини, …) і прайсом.
**Хто веде проєкт:** QA-інженер, не розробник. Тому:

- пояснюй рішення простою мовою, без жаргону (або з коротким поясненням терміну);
- кожна зміна покривається автотестами (розділ 8), а не ручним чек-листом;
- не роби «магії» — краще 3 зрозумілі файли, ніж 1 розумний.

## 2. Головні правила роботи (ОБОВ'ЯЗКОВО)

1. **Сумнівайся.** Перед будь-яким рішенням (бібліотека, структура, сервіс) — коротко назви 2–3 варіанти, плюси/мінуси, і свою рекомендацію. Не приймай рішення мовчки.
2. **Сумнівайся і в вимогах.** Якщо вимога неясна або здається зайвою — запитай, а не вигадуй. Список відкритих питань — розділ 10.
3. **Не переускладнюй.** Правило: якщо можна без бекенду, бази даних, авторизації, фреймворку — роби без них. Кожна нова залежність потребує обґрунтування одним реченням.
4. **Малі кроки.** Одна задача = одна зміна, яку можна перевірити в браузері за 5 хвилин.
5. **Тести.** Нова функціональність = новий або оновлений тест. Після кожної зміни запусти `npm test`; зміна вважається готовою лише тоді, коли тести зелені. Звіти й ручні чек-листи не потрібні.
6. **Не видаляй і не перезаписуй фото замовника** без явного підтвердження.

## 3. Варіанти реалізації (вибір ще НЕ зафіксовано)

| Варіант | Суть | Плюси | Мінуси | Коли обрати |
|---|---|---|---|---|
| **A. Конструктор** (Tilda / Wix / Framer) | Без коду, готові шаблони галерей | Найшвидше, фотограф сам редагує, хостинг включено | Щомісячна оплата, залежність від платформи, обмежена гнучкість | Якщо бюджет малий і ніхто не буде підтримувати код |
| **B. Статичний сайт + проста адмінка** ⭐ | Astro + фото в репозиторії + Decap CMS / Pages CMS для редагування | Безкоштовний хостинг, дуже швидкий, повний контроль, фотограф може міняти прайс і фото через веб-інтерфейс | Потрібен хтось технічний для старту, адмінка простіша за Tilda | **Рекомендовано за замовчуванням** |
| **C. Headless CMS + фреймворк** (Next.js + Sanity/Strapi) | Повноцінна CMS | Зручна адмінка, масштабується | Надлишково для портфоліо, більше точок відмови | Лише якщо з'являться блог, бронювання, кабінет клієнта |

> ⚠️ Перед стартом розробки чесно обговорити з замовником варіант A. Якщо він кращий для бізнесу — це нормальний результат.

Далі в документі описано **варіант B**.

## 4. Стек (варіант B)

| Що | Вибір | Альтернатива | Чому так |
|---|---|---|---|
| Генератор сайту | **Astro** | Eleventy, чистий HTML | Вбудована оптимізація фото (`<Picture>`), мало JS у браузері |
| Стилі | **Звичайний CSS** (один файл + змінні) | Tailwind | Менше залежностей, легше читати QA |
| Лайтбокс (перегляд фото на весь екран) | **PhotoSwipe v5** | GLightbox, власний `<dialog>` | Зрілий, свайпи на мобільному, клавіатура |
| Фото | **У репозиторії** `src/assets/photos/` | Cloudinary / Cloudflare R2 | Простіше на старті. Переходити на CDN, якщо фото > ~500 МБ |
| Контент (категорії, прайс) | **Markdown/JSON файли** в `src/content/` | CMS | Можна правити руками або через адмінку |
| Адмінка для фотографа | **Decap CMS** (опційно) | Pages CMS, без адмінки | Безкоштовно, працює поверх тих самих файлів |
| Форма зв'язку | **Немає — посилання на Telegram / Viber / Instagram / телефон** | Netlify Forms, Formspree | Фотографам зазвичай пишуть у месенджери. Без бекенду = нема чого ламати |
| Хостинг | **Cloudflare Pages** або **Netlify** | Vercel, GitHub Pages | Безкоштовно, автодеплой з Git, HTTPS |
| Тести | **Playwright** + `@axe-core/playwright` | Cypress | Тестує сайт як користувач, мобільні в'юпорти, WebKit (iOS Safari), знайомий QA інструмент |

## 6. Фото — найважливіша частина

- **Оригінали не комітити.** Перед додаванням: довга сторона ≤ 2500 px, JPEG ~80%, розмір файлу ≤ ~800 КБ.
- **Видаляти EXIF/GPS** (приватність клієнтів — у фото може бути адреса).
- Astro генерує WebP/AVIF і кілька розмірів (`srcset`) автоматично через `<Picture>`.
- Ліниве завантаження (`loading="lazy"`) для всіх фото, крім першого екрана.
- Кожне фото має `alt` (доступність + SEO). Якщо нема — генерований за категорією, але краще вручну.
- Кількість на категорію: **20–40 найкращих**, не весь архів.
- **Хрестини / діти:** публікувати лише з дозволу батьків. Це питання до замовника, не до коду.
- **Повні галереї для клієнтів** (віддати 500 фото з весілля) — **поза скоупом**. Для цього є Pixieset / Pic-Time / Google Drive. Не будувати самим.
- Захист від копіювання: заборона ПКМ не працює і дратує. Варіанти: водяний знак (питання до замовника) або нічого.

## 7. Нефункціональні вимоги

Кожна вимога перевіряється автотестом (файл вказано в дужках):

- Mobile-first: 360 px, 768 px, 1280 px+ (усі тести запускаються на кількох в'юпортах)
- Лайтбокс: свайп, стрілки клавіатури, Esc закриває (`gallery.spec.ts`)
- Посилання на месенджери мають коректний формат (`links.spec.ts`)
- Унікальні `title`/`description`, OG-картинка, `sitemap.xml`, `robots.txt`, `lang="uk"` (`seo.spec.ts`)
- Немає помилок у консолі браузера (`smoke.spec.ts`)
- Немає фото > 1 МБ у `dist/`, немає GPS в EXIF (`images.spec.ts`)
- Немає серйозних порушень доступності (`a11y.spec.ts`)
- Збірка `npm run build` проходить без помилок
- Мультимовність — лише якщо замовник попросить

## 8. Тести

### Підхід — варіанти

| Варіант | Що дає | Коли |
|---|---|---|
| **Playwright e2e** ⭐ | Перевіряє зібраний сайт у браузері як користувач | **Основа, з першого дня** |
| + axe-core | Автоперевірка доступності | Разом із Playwright, це один рядок у тесті |
| Lighthouse CI | Бали продуктивності | Пізніше, якщо швидкість стане проблемою. Бали нестабільні між запусками |
| Vitest (unit) | Тести окремих функцій | **Поки не потрібно**: логіки майже немає. Додавати, коли з'явиться функція з умовами |
| Скріншот-тести | Ловлять зміни верстки | Не на старті: багато хибних падінь при оновленні фото |

### Структура

```
tests/
├── helpers/content.ts   # читає galleries/*.md і prices.json — тести беруть дані звідси
├── smoke.spec.ts        # кожна сторінка відкривається (200), немає помилок у консолі, неіснуюча сторінка → 404
├── gallery.spec.ts      # кожна категорія з контенту має сторінку, фото видно, лайтбокс: відкрити / → / ← / Esc / свайп
├── prices.spec.ts       # кількість карток = кількість пакетів у prices.json, ціна відформатована («від 15 000 ₴»)
├── links.spec.ts        # href у контактах: https://t.me/…, viber://…, https://instagram.com/…, tel:+380…
├── seo.spec.ts          # унікальні title/description, og:image, sitemap.xml, robots.txt, lang="uk"
├── a11y.spec.ts         # axe: 0 critical/serious; у всіх <img> є непорожній alt
└── images.spec.ts       # після build: файли в dist/ ≤ 1 МБ, у src/assets/photos немає EXIF GPS
```

### Правила

- **Тести керуються даними.** Список категорій і пакетів береться з `src/content/`, тому нова категорія автоматично потрапляє в тести без їх правки.
- Тести запускаються проти **зібраної** версії (`npm run build && npm run preview` через `webServer` у `playwright.config.ts`), а не dev-сервера.
- Проєкти (браузери): Desktop Chrome, Pixel 7 (Android), iPhone 14 (WebKit).
- Селектори: `data-testid` або ролі (`getByRole`). Не CSS-класи.
- Без `waitForTimeout`: чекати конкретний стан (`toBeVisible`, `toHaveURL`).
- Зовнішні посилання не відкривати в тестах, лише перевіряти `href`.
- CI (опційно): GitHub Actions запускає `npm test` на кожен push. Хостинг не деплоїть, якщо тести впали.

## 9. Команди

```bash
npm install                    # встановити залежності (один раз)
npx playwright install         # завантажити браузери для тестів (один раз)
npm run dev                    # локальний сайт на http://localhost:4321
npm run build                  # зібрати продакшн-версію в /dist
npm run preview                # переглянути зібрану версію
npm test                       # build + усі автотести
npx playwright test --ui       # тести з візуальним інтерфейсом (зручно для дебагу)
npx playwright show-report     # HTML-звіт останнього запуску
```

## 10. Відкриті питання до замовника

1. Які саме категорії? (весілля, хрестини, love story, сімейні, дитячі, студійні, …)
2. Хто оновлюватиме сайт — фотограф сам чи «технічна людина»? → визначає варіант A/B і чи потрібна адмінка.
3. Прайс: точні ціни чи «від»? Пакети? Як часто змінюється?
4. Чи є домен? Бюджет на щомісячні платежі (0 ₴ / до 500 ₴)?
5. Водяний знак на фото — так/ні?
6. Дозволи на публікацію фото клієнтів, особливо дітей?
7. Як клієнти зв'язуються зараз? (Instagram Direct, Telegram, Viber, дзвінок) → які кнопки ставити.
8. Брендинг: логотип, кольори, шрифти — є чи робимо мінімалістично (білий/чорний фон, фото в центрі уваги)?
9. Чи потрібна стрічка Instagram на сайті? (Рекомендація: **ні** — API Instagram нестабільний, достатньо посилання.)
10. Відгуки клієнтів — потрібні? Лише реальні, з дозволу.

## 11. Чого НЕ робити (без окремого погодження)

- Бекенд, база даних, авторизація, особистий кабінет
- Онлайн-оплата, онлайн-бронювання з календарем
- Блог
- Вбудована стрічка Instagram
- Анімації, паралакс, «вау-ефекти», що гальмують мобільний
- Заборона правої кнопки миші
- Нові npm-пакети без пояснення «навіщо і чим замінити»
