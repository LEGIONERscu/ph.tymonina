# Skill: сайт-портфоліо фотографа

Цей skill доповнює `CLAUDE.md`. Спочатку прочитай `CLAUDE.md` (архітектура, стек, тести, обмеження).
Користувач — QA, не розробник: пояснюй просто. Якість підтверджується автотестами, а не звітами.

## Крок 0. Перед будь-якою задачею — «адвокат диявола»

Перш ніж писати код, дай коротку відповідь (5–10 рядків):

1. **Що я зрозумів** — задача своїми словами.
2. **Сумніви** — що в задачі неясно, суперечливо або, можливо, не потрібно.
3. **Варіанти** — 2–3 способи реалізації:
   - мінімальний (найпростіше, що працює);
   - рекомендований;
   - «більш потужний» (лише якщо є причина).
   Для кожного: плюси, мінуси, нові залежності.
4. **Рекомендація** + чому.
5. Якщо зміна зачіпає > 3 файлів або додає залежність — **дочекайся підтвердження**.

Якщо задача дрібна і очевидна (виправити текст, поміняти ціну) — крок 0 можна скоротити до одного речення.

## Останній крок будь-якої задачі — тести

1. Зміна поведінки → онови або додай тест у `tests/` (див. «Як писати тести»).
2. Запусти `npm test`.
3. Червоні тести → виправ код (не тест!). Міняти тест можна лише якщо змінилась сама вимога — тоді скажи про це явно.
4. Задача завершена, лише коли всі тести зелені.

## Сценарій 1. Додати нову категорію (напр. «Love Story»)

1. Узгодь `slug` латиницею: `love-story` (транслітерація, без пробілів, нижній регістр).
2. Створи папку `src/assets/photos/love-story/`.
3. Підготуй фото (див. «Підготовка фото» нижче).
4. Створи `src/content/galleries/love-story.md` за зразком з `CLAUDE.md` (розділ 5). Заповни `title`, `order`, `cover`, `description`.
5. Код сторінок і тестів НЕ змінюй — категорія підхоплюється автоматично. Якщо довелось змінити код — це сигнал, що архітектура зламана; повідом.
6. `npm test` — нова категорія автоматично перевіряється в `gallery.spec.ts`, `seo.spec.ts`, `images.spec.ts`.

## Сценарій 2. Додати / замінити фото в категорії

1. Підготуй фото (нижче).
2. Поклади у відповідну папку категорії. Імена: `01.jpg`, `02.jpg`… (порядок = ім'я) або впиши порядок у `photos:` у `.md`.
3. Додай `alt` для кожного нового фото (без нього впаде `a11y.spec.ts`).
4. Старі фото видаляти лише після явного «так» від користувача.
5. `npm test`.

### Підготовка фото

- Довга сторона ≤ 2500 px, JPEG якість ~80, файл ≤ ~800 КБ.
- Видалити EXIF (особливо GPS) — інакше впаде `images.spec.ts`.
- Варіанти інструментів (запропонуй користувачу, не нав'язуй):
  - без встановлення: squoosh.app (вручну, по одному);
  - пакетно: скрипт `scripts/prepare-photos` на базі `sharp` (вже є в залежностях Astro; додавати скрипт лише якщо фото багато і часто);
  - macOS: «Попередній перегляд → Експорт» або ImageOptim.
- Діти на фото → перепитай, чи є дозвіл на публікацію.

## Сценарій 3. Оновити прайс

1. Редагуй лише `src/content/prices.json`.
2. Ціни — числом, без пробілів і «грн» (`15000`, не `"15 000 грн"`). Форматування робить компонент.
3. Невалідний JSON або пропущене поле — збірка впаде через схему в `config.ts`. Так і задумано.
4. `npm test` — `prices.spec.ts` звірить кількість карток і форматування з файлом.

## Сценарій 4. Нова сторінка або блок

1. Крок 0 обов'язковий. Спершу спитай: «Чи можна обійтися блоком на існуючій сторінці?»
2. Сторінка = файл у `src/pages/`, використовує `BaseLayout.astro`.
3. Повторюваний шматок (> 1 використання) → компонент у `src/components/`. Одноразовий — лишай у сторінці, не виносити «на майбутнє».
4. Додай URL сторінки в `smoke.spec.ts` і `seo.spec.ts` (якщо список сторінок там не генерується автоматично).
5. Новий інтерактив (кнопка, меню, форма) → окремий тест його поведінки.

## Сценарій 5. Додати бібліотеку / сервіс

Перед встановленням відповідай на 4 питання:
1. Яку проблему вирішує?
2. Чи можна без неї (звичайний HTML/CSS/кілька рядків JS)?
3. Розмір і чи підтримується (останній реліз < 1 року)?
4. Що буде, якщо її доведеться прибрати?

Якщо хоч одна відповідь слабка — пропонуй варіант без бібліотеки.

## Як писати тести

**Інструмент:** Playwright (+ `@axe-core/playwright` для доступності). Структура файлів — у `CLAUDE.md`, розділ 8.

**Правила:**
- Дані — з `tests/helpers/content.ts` (читає `src/content/`), не хардкодити назви категорій і ціни.
- Селектори: `getByRole`, `getByText`, `data-testid`. Не CSS-класи і не XPath.
- Без `waitForTimeout` — лише очікування стану (`toBeVisible`, `toHaveURL`, `toHaveCount`).
- Один тест = одна поведінка. Назва тесту описує очікування: `"Esc закриває лайтбокс"`.
- Зовнішні сервіси (Instagram, Telegram) не відкривати — перевіряти лише `href`.
- Тест має падати, якщо функціональність зламати. Перевір це один раз, коли пишеш новий тест: тимчасово зламай код → тест червоний → поверни.

**Що обов'язково покрито (не видаляти ці тести):**
- кожна сторінка і кожна категорія відкривається без помилок у консолі;
- неіснуюча сторінка → 404;
- лайтбокс: відкриття, →, ←, Esc, свайп на мобільному;
- прайс відповідає `prices.json`;
- формат посилань на месенджери і телефон;
- SEO-мета, sitemap, robots, `lang="uk"`;
- axe: 0 critical/serious, у всіх фото є `alt`;
- розмір файлів у `dist/` і відсутність GPS в EXIF.

**Негативні сценарії** (додавати як тести, коли відповідна логіка з'явиться):
- категорія без фото → сторінка не падає, показує заглушку;
- дуже довга назва пакета → немає горизонтального скролу (`scrollWidth <= clientWidth`);
- вимкнений JS (`javaScriptEnabled: false`) → фото галереї видно.

**Приклад:**

```ts
import { test, expect } from '@playwright/test';
import { galleries } from './helpers/content';

for (const g of galleries) {
  test(`${g.title}: лайтбокс відкривається і закривається по Esc`, async ({ page }) => {
    await page.goto(`/portfolio/${g.slug}`);
    await page.getByTestId('gallery-item').first().click();
    const lightbox = page.getByRole('dialog');
    await expect(lightbox).toBeVisible();
    await page.keyboard.press('Escape');
    await expect(lightbox).toBeHidden();
  });
}
```
